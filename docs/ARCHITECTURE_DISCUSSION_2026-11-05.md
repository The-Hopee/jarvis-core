# Обсуждение архитектуры и скорости — 5 ноября 2026

Это запись требований и предлагаемой реализации, а не отчёт об уже внедрённой
оптимизации. Живые проверки аккаунтов и кодящего режима перечислены в
[NEXT_SESSION.md](NEXT_SESSION.md). Основная жалоба пользователя: около 40 секунд
до голосового ответа. Режим ML-менторства остаётся отдельной задачей.

## Что подтверждено текущим кодом и локальной проверкой

- Конвейер синхронный: Vosk дожидается завершённой фразы, затем OpenRouter
  Scribe v2 уточняет готовую запись, затем модель вызывает инструменты и формирует
  полный ответ, затем Fish s2.1-pro синтезирует голос. request_audio читает весь
  ответ в память; файл записывается и только потом передаётся проигрывателю.
- Микрофон закрыт на время транскрибации, модели, инструментов и озвучивания.
- Для произвольного запроса Assistant может сделать до шести последовательных
  обращений к модели. Инструменты исполняются последовательно. Запуск известных
  приложений уже имеет быстрый локальный путь, но контекстная реплика ждёт модель.
- Текущие модели: openai/gpt-4.1-mini, elevenlabs/scribe-v2,
  fish-audio/s2.1-pro. Голос A: локальный WAV-образец 15,02 с / 24 кГц,
  721 022 байта, передаётся с каждым новым запросом синтеза. Изменение голоса
  пользователь сейчас не просил. Короткие точные реплики уже воспроизводятся
  из локального манифеста.
- 40 секунд JARVIS_CONVERSATION_SECONDS — окно продолжения разговора после
  ответа; оно не добавляет обязательную сорокасекундную паузу перед ответом.
- Кодящий контур уже фоновый: start_job запускает отдельный процесс; внутри
  Orchestrator до двух исполнителей работают в отдельных Git worktree.
  Общей устойчивой очереди заданий, фоновых голосовых уведомлений и глобального
  ограничения конкурентности нескольких coding jobs пока нет.
- Аппаратная конфигурация проверки: i5-11400F, около 32 ГиБ ОЗУ,
  RTX 3060 12 ГиБ. Это основание включить GPU-ASR в эксперимент, но не
  доказательство его скорости/точности на этой машине. Новые модели не загружали.

Обезличенный разбор имеющихся логов: десять завершённых обращений 5 ноября.
Распознанный текст логируется ПОСЛЕ облачного ASR; голосовой ответ логируется
ДО синтеза. Интервал до следующей строки микрофона включает полную речь.

| Наблюдаемый интервал | Медиана | Диапазон |
| --- | ---: | ---: |
| Распознанный текст → готовый текст ответа, включая инструменты | 2,147 с | 0–6,057 с |
| Готовый текст → возвращение микрофона, включая TTS и воспроизведение | 12,640 с | 1,827–54,511 с |

Это небольшая неконтролируемая выборка разных команд и ответов; в ней нет
отдельных отметок конца речи, времени ASR и начала звука. Нельзя объявлять её
полным замером задержки пользователя или приписать весь второй интервал TTS.
Длинные ответы также долго произносятся: для ответа в 625 символов второй
интервал составил 54,511 с. В истории всех просмотренных логов одна отметка
резервного голосового движка и ноль отметок ошибки облачного ASR; это не
исключает медленных успешных запросов. Новых платных вызовов для этого разбора
не делали, тексты разговоров в документ не копировали.

## Сначала измерить, затем менять узкие места

Для каждого обращения нужен request_id и monotonic timestamps:
speech_end → endpoint_final → asr_start/asr_final → route_selected →
llm_start/first_token/final (для каждого обращения) → tool_start/end →
tts_start/first_audio_byte → playback_start/end. Дополнительно учитывать
ожидание очереди, холодный старт, сетевую ошибку, резервный провайдер и стоимость.
В лог метрик писать длительности и названия операций без аудио, секретов,
содержимого личных сообщений и документов.

Основная метрика: конец речи пользователя → начало содержательного голосового
ответа. Отдельно считать время быстрого подтверждения, завершения действия и
освобождения микрофона; короткое «Принято» не выдавать за готовый результат.
Сравнивать медиану и p95 на одинаковых заданиях; разделять холодные/прогретые
запуски и короткие/длинные реплики.

Порядок оптимизации:

1. Замеры этапов и короткий голосовой ответ на бытовые команды. Длинные тексты,
   код и содержимое документа сохранять в артефакте, озвучивать итог и по просьбе
   подробности. Успешное действие подтверждать после фактического результата.
2. Подтверждения/статусы воспроизводить из заранее подготовленного локального
   кэша выбранного голоса. Запускать после принятия задачи, не ждать облачного
   синтеза статуса. Один статус через разумный порог ожидания, следующий — при
   реальной смене этапа, без постоянного повторения и перебивания пользователя.
3. Потоковый вывод модели и TTS: буферизовать целое короткое предложение,
   начать его озвучивание, продолжая готовить следующие. Где маршрут поддерживает
   поток аудиобайтов, воспроизводить по мере поступления, без ожидания полного
   файла. Проверить реальное время первого байта именно Fish с голосом A;
   документированная передача потока не гарантирует мгновенную выдачу провайдера.
   Сохранять порядок частей, единый голос, отменять устаревшие статусы/части.
   Вызов инструмента исполнять только после полной валидации его аргументов;
   промежуточный текст модели не означает успешное действие.
4. Надёжные частые команды отправлять в локальный обработчик без отдельного
   запроса LLM для выбора инструмента. Не ослаблять проверку адресата, схемы
   аргументов и правила неопределённого результата отправки.
5. Сравнить ASR и VAD. Настройка окончания фразы — отдельный источник задержки:
   короткая пауза не всегда означает конец диктовки, слишком агрессивное
   завершение режет имена/сообщения. Ввести отдельные параметры для команды
   и длинной диктовки, измерять частоту преждевременного завершения.
6. После замеров — постоянные HTTP/WS-соединения, прогретые локальные модели,
   минимальный нужный контекст, подходящий провайдер модели и ограничение
   количества ненужных обращений. Увеличение мощности модели само по себе
   не является способом уменьшить задержку.

Инженерные ориентиры для проверки: локальное подтверждение в пределах 0,5–1 с
после принятия команды, короткие обычные голосовые ответы ориентировочно за
2–5 с от конца речи в прогретом режиме. Это цели следующего эксперимента,
а не достигнутые результаты или гарантии для тяжёлых задач/сетевых сбоев.

## Кандидаты распознавания

Не назначать победителя по чужому графику. Подготовить 30–50 одинаковых русских
фраз: VS Code/ONLYOFFICE, названия треков и исполнителей, имена и username,
длинная диктовка, тихая речь, музыка на фоне, смешанные русские/английские слова.
Хранить для сравнения только специально подготовленные тестовые записи, если
пользователь их предоставит; повседневный микрофон автоматически не архивировать.
Проверять не только WER/CER, но точное действие, получателя, имена и сохранность
продиктованного текста, задержку финального результата и стоимость минуты.

| Кандидат | Что проверять |
| --- | --- |
| Текущий Scribe v2 через OpenRouter | Базовая точность и реальная задержка готовой записи |
| Whisper large-v3-turbo через OpenRouter | Быстрый файловый маршрут с тем же ключом; доступен в каталоге STT |
| Scribe v2 Realtime напрямую | Потоковое распознавание по WebSocket; отдельное подключение ElevenLabs |
| Voxtral Mini Transcribe Realtime 3 напрямую | Поток, встроенное определение конца фразы, русский; публичный preview |
| Локальный faster-whisper, например large-v3-turbo/small | Точность и время на RTX 3060, нагрузка GPU, память и холодный старт |

faster-whisper сам по себе не делает готовую файловую модель полноценной
потоковой: для чанков и стабильного финала нужен дополнительный конвейер.
В каталоге OpenRouter transcription есть Scribe v2 и Whisper large-v3-turbo;
точных Scribe v2 Realtime и Voxtral Mini Transcribe Realtime 3 в нём при проверке
не было. Модели со словом streaming в имени могут обслуживаться файловым HTTP
endpoint. Нужен документированный транспорт живого потока, одной замены имени
модели недостаточно. Основной LLM при прямом ASR остаётся в OpenRouter.

Поток запускать после локального обращения «Джарвис», с коротким кольцевым
буфером в памяти для начала команды. Не отправлять непрерывный звук комнаты.
Промежуточный ASR нужен для отображения/подготовки, действия с последствиями
исполнять по стабильному финальному тексту. Гарантировать отзывчивость при
одновременной речи помощника можно только после работы с эхом и barge-in;
асинхронный Python сам эту проблему не решает.

## Три профиля и маршрутизация

Домен задачи, её сложность и глубина рассуждения — разные оси. Сложный анализ
документа может потребовать сильной модели, небольшая правка кода — дешёвой.
«Академическая сложность» и длина запроса в одиночку недостаточны. Учитывать
число зависимых действий, требуемую точность, объём контекста, доступные tools,
неопределённость, предыдущие неудачи и бюджет. Не доверять одному самооценочному
числу уверенности LLM; проверять результат инструментами и тестами.

| Профиль | Предлагаемые кандидаты, ещё не включены |
| --- | --- |
| Повседневный | Локальные команды + дешёвая tool-модель; сравнить текущую GPT-4.1-mini и GPT-6 Luna с малой глубиной рассуждения |
| Документы | GPT-6.1 Terra как кандидат для текста/визуальной работы; простое заполнение шаблонов детерминированными функциями |
| Кодинг/тяжёлое рассуждение | GPT-6 Sol high/xhigh или Claude Opus 5 medium/high; разные роли мастера, исполнителя и ревьюера |

Публичный каталог OpenRouter проверен без платной генерации: gpt-6-sol,
claude-opus-5, gpt-6.1-terra, gpt-6-luna перечислены с tools и reasoning.
ID gpt-6-terra отсутствует; исправление имени не является автоматическим
разрешением менять уже используемую модель. Реальные доступ/баланс/совместимость
параметров конкретного маршрута проверять минимальным интеграционным вызовом.
По документации OpenAI GPT-6.1 Terra использует Responses API для tools, а GPT-6
Sol в Chat Completions ограничивает tools режимом reasoning none. Текущий клиент
Jarvis использует Chat Completions. Поэтому перед high/xhigh с инструментами
нужны совместимый Responses-адаптер или проверенная нормализация OpenRouter;
наличие строки tools в каталоге этого ещё не доказывает. Названия усилий у разных
провайдеров сопоставлять отдельно. Claude Opus 5 существует, в текущем каталоге
Anthropic помечен active/legacy; выбирать заявленную пользователем версию без
скрытой подмены на другую.

Порядок маршрутизации: точная локальная команда → правила выбора домена →
маленький классификатор только для неоднозначного запроса → выбранный исполнитель.
Передавать модели только относящиеся к задаче скиллы, а не всю библиотеку.
При провале проверки повышать уровень ограниченно; не повторять уже выполненную
отправку/другое действие из-за смены модели. Сохранить команды явного выбора
режима и задавать лимит стоимости/шагов для тяжёлого задания.

Каждый скилл: понятное назначение и условия выбора, входная схема, реальные tools,
критерий успеха, обработка ошибок, ограничения совместного ресурса, проверочные
примеры. Количество скиллов само по себе не гарантирует качество: дублирующиеся
инструкции и огромный общий prompt увеличивают задержку и ошибочный выбор.

## Фоновые задачи и окна Windows

Предлагаемый диспетчер: лёгкий asyncio-процесс принимает обращения и события;
блокирующие I/O-операции выполняют ограниченные workers, тяжёлый локальный
ASR — отдельный процесс/выделенный worker. Приём задания возвращает job_id,
после чего диалог доступен для нового вопроса и запроса состояния.

Первый вариант: SQLite хранит job_id, зависимости, приоритет, текущий этап,
результат и состояние отмены; ограниченная очередь в процессе раздаёт задания.
Состояния: queued/running/waiting_user/succeeded/failed/cancelled; неопределённый
результат внешнего действия сохранять отдельно как uncertain, не повторять
автоматически при восстановлении. Redis/RabbitMQ потребуется при обоснованном
переходе к нескольким независимым сервисам/машинам; брокер не сокращает время
выполнения одного сетевого запроса и не разрешает конфликты сам по себе.

События инструментов и работников дают честные статусы «ищу трек», «запускаю
проверки», «сохраняю документ». Статусы не выдумывает LLM. Диспетчер речи — один,
он ставит уведомления в очередь, отменяет устаревшие и не накладывает два голоса.
Асинхронность не убирает зависимости: погоду нельзя пересказать раньше получения
погоды, а чужому адресату нельзя отправить ещё не проверенный текст. Длительные
блокирующие вызовы должны поддерживать таймауты и кооперативную отмену;
отмена coroutine не останавливает уже работающий поток или внешнюю отправку.

На одном интерактивном рабочем столе Windows общий foreground/input focus,
курсор и клавиатура. Два одновременно открытых окна работают, но две параллельные
цепочки физических кликов/ввода могут мешать друг другу. Операции GUI отправлять
одному исполнителю с блокировкой на целую последовательность действий.

Параллельно с ним могут работать Telegram API, запросы погоды, генерация DOCX,
модели и кодящие процессы: им не требуется foreground. Browser DOM/CDP и UIA
patterns часть задач выполняют без физических кликов, но это проверяется для
конкретного приложения. Общий профиль VK/сессия/проигрыватель остаются ресурсами:
музыка и диалоги сейчас используют одного worker, профиль открывает один владелец.
Разные вкладки сами по себе не дают безопасной конкурентности.

Блокировки: документ — на целый цикл чтение/изменение/сохранение; Telegram —
на клиент/сессию и порядок в одном диалоге; VK — на профиль/плеер; код — по
пересекающимся файлам и интеграции; физический GUI — один исполнитель; звук —
один проигрыватель. Для полного независимого GUI впоследствии подходят отдельные
сессии/VM; виртуальный рабочий стол Windows не создаёт второй независимый курсор.

## Предлагаемый порядок следующей реализации

1. Метрики и воспроизводимый набор команд; кэшированные статусы и короткие ответы.
2. Потоковое аудио с выбранным голосом A; затем потоковый текст и ASR по замерам.
3. Единая очередь, статусы/уведомления/отмена, ограничения ресурсов; подключить
   к ней уже существующие кодящие процессы.
4. Три профиля с явным выбором, затем проверяемая автоматическая маршрутизация.
5. Живые сценарии VK/TG и отдельный кодящий demo; результаты занести в VALIDATION.

Базовые автоматические проверки этих функций уже существуют; в этой сессии
изменена документация, поэтому повторный прогон всех 84 тестов не выполнялся.
Живые отправки сообщений и воспроизведение музыки этой записью не проверены.
